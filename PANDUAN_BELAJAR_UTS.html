3. Skenario Demo di Depan Dosen (Step-by-Step)

Urutan pengujian terstruktur untuk menunjukkan seluruh logika dan alur sistem:

Skenario A: Demo Pelanggan (Jack Kurniawan)

1. Buka Katalog Perlengkapan Outdoor (/shop)
Tunjukkan katalog produk bertema alam bebas (Tenda, Carrier, Sepatu, Jaket Gore-Tex, Sleeping Bag). Tunjukkan fitur pencarian, filter kategori, dan status stok realtime.
2. Keranjang Belanja & Validasi Stok Gudang (/cart)
Tambahkan produk ke keranjang belanja. Coba ubah kuantitas melebihi batas stok gudang: sistem akan menolak dan memberikan pesan peringatan error secara otomatis.
3. Checkout & Payment Gateway ApexPay
Isi alamat pengiriman dan pilih metode pembayaran:
• QRIS: Tampilan QR Code standar GPN dengan NMID resmi dan countdown timer.
• Virtual Account: Nomor VA Bank unik (BCA, Mandiri, BNI, BRI) dengan fitur satu-klik salin.
• E-Wallet: GoPay, OVO, DANA.
4. Simulasi Pelunasan Webhook
Klik tombol "Konfirmasi Pembayaran Sukses (Simulasi)". Jelaskan ke dosen: "Server mengeksekusi lockForUpdate(), memotong stok alat di gudang secara atomik, dan menerbitkan struk lunas."
5. Cetak Faktur / Struk & Laporan Belanja
Tunjukkan halaman struk yang siap cetak (Ctrl+P) dan menu Laporan Belanja Pelanggan untuk melihat total belanja Jack Kurniawan.

Skenario B: Demo Backoffice & Hak Akses Pembatalan Owner

1. Login sebagai Owner (admin@mail.com)
Tunjukkan Executive Dashboard Chart.js: diagram donat perbandingan penjualan Kasir POS vs Toko Online, ringkasan omset otomatis, dan peringatan stok menipis (≤ 5 unit).
2. Alur Pembatalan Transaksi Eksklusif Owner
Tunjukkan bahwa tombol pembatalan transaksi POS maupun pesanan pelanggan hanya muncul dan dapat dijalankan oleh akun Owner. Ketika dibatalkan, kuantitas stok otomatis dikembalikan ke inventaris.
3. Pusat Laporan Bisnis (/reports)
Tunjukkan laporan keuangan komprehensif: Omset POS, Pesanan Online, Pembelian Modal Gudang, dan Estimasi Laba Kotor dengan filter rentang tanggal dan tombol cetak PDF resmi.

4. Pertanyaan Ujian Dosen & Kunci Jawabannya

Q1: "Harga saat checkout diambil dari mana? Apakah pembeli bisa memodifikasi harga via inspect element?"
Jawaban: "Tidak bisa dimanipulasi, Pak/Bu. Sistem menerapkan Strict Server-Side Pricing di CheckoutController.php. Input harga dari client diabaikan sepenuhnya; server mengambil harga resmi langsung dari database via Product::findOrFail($id)->selling_price di dalam DB::transaction()."
Q2: "Bagaimana sistem mencegah race condition saat dua pembeli memesan stok terakhir bersamaan?"
Jawaban: "Sistem menggunakan row-level lock Product::lockForUpdate() pada database MariaDB. Baris data produk dikunci selama proses pembayaran. Jika pembeli pertama berhasil, pembeli kedua akan menerima pesan bahwa stok tidak mencukupi dan sistem otomatis melakukan rollback."
Q3: "Bagaimana aturan pembatalan transaksi diimplementasikan?"
Jawaban: "Sesuai kebijakan keamanan toko, hak pembatalan transaksi eksklusif milik Owner/Administrator melalui middleware can:admin-only di routes/web.php dan pengecekan otorisasi di Controller. Staff kasir dan pelanggan tidak memiliki hak membatalkan transaksi tanpa verifikasi Owner."
Q4: "Mengapa tabel products menggunakan Soft Deletes?"
Jawaban: "Untuk menjaga integritas referensial data masa lalu (Historical Audit Trail). Jika produk dihapus dari katalog, transaksi kasir lama dan pesanan online yang pernah memuat produk tersebut tidak akan rusak atau error."

5. Ringkasan ERD Database (11 Tabel)

+------------------+ +-------------------+ +--------------------+ | CATEGORIES | 1 --- N | PRODUCTS | 1 --- N | ORDER_ITEMS | +------------------+ +-------------------+ +--------------------+ | id (PK) | | id (PK) | | id (PK) | | name | | category_id (FK) | | order_id (FK) | +------------------+ | sku, name, stock | | product_id (FK) | | purchase_price | | quantity, subtotal | | selling_price | +---------+----------+ +---------+---------+ | N | | | 1 | 1 +------------------+ +---------+---------+ +---------+----------+ | SUPPLIERS | 1 --- N | PURCHASE_ITEMS | | ORDERS | +------------------+ +-------------------+ +--------------------+ | id (PK) | | id (PK) | | id (PK) | | name, phone | | purchase_id (FK) | | user_id (FK) | +--------+---------+ | product_id (FK) | | order_number | | | quantity, subtotal| | customer_name | | 1 +---------+---------+ | total_amount | | | | status | | N | N +---------+----------+ +--------+---------+ | | 1 | PURCHASES | | 1 | +------------------+ +---------+---------+ | 1 | id (PK) | | SALE_ITEMS | +---------+----------+ | supplier_id (FK) | +-------------------+ | PAYMENTS | | user_id (FK) | | id (PK) | +--------------------+ | purchase_number | | sale_id (FK) | | id (PK) | +--------+---------+ | product_id (FK) | | order_id (FK) | | | quantity, subtotal| | payment_method | | N +---------+---------+ | transaction_code | | | | amount, status | | 1 | N +--------------------+ +--------+---------+ | | USERS | 1 --------------- + 1 (SALES / Kasir POS) +------------------+ | id (PK) | | name, email | | role (enum) | +------------------+

Kardinalitas Kunci:

  • Categories ke Products (1 : N): 1 kategori outdoor mengelompokkan banyak produk alat.
  • Users ke Orders (1 : N): 1 akun customer (Jack Kurniawan) dapat memiliki banyak pesanan online.
  • Orders ke Order_Items (1 : N): 1 pesanan online menampung satu atau banyak item belanjaan.
  • Orders ke Payments (1 : 1): 1 pesanan online terhubung tepat ke 1 sesi transaksi ApexPay Gateway.
  • Suppliers ke Purchases (1 : N): 1 supplier memasok banyak transaksi pembelian stok masuk gudang.
  • Sales ke Sale_Items (1 : N): 1 struk kasir toko fisik mencatat banyak rincian barang.
